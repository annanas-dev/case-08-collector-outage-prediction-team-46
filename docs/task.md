# ТЗ: Сервис прогнозирования инцидентов и управления ремонтными работами инженерных коллекторов Москвы

Заказчик: Департамент ЖКХ города Москвы, эксплуатант: АО «Москоллектор». Хакатон «Лидеры цифровой трансформации», 2026.

Расшифровка PDF `archive/tz/8. ДЖКХ.pdf` (16 стр.). Номера разделов совпадают с оригиналом. Термины: [glossary.md](glossary.md).

**Кратко:** по историческим и текущим данным датчиков предсказывать инциденты (отказы оборудования, пожар, подтопление, проникновение) с вероятностью, горизонтом не менее 24 ч и локацией, выдавать рекомендации по ТО и показывать всё диспетчеру в веб-дашборде. Решения принимает человек, сервис только советует.

---

## 2. Контекст

АО «Москоллектор» эксплуатирует 825 км коллекторов, 19,7 тыс. км кабелей связи, 8,3 тыс. км силовых кабелей, 1,9 тыс. км теплотрасс и водопроводов.

Проблемы текущего подхода:
- реактивная работа: реагируют только после срабатывания датчика;
- ложные тревоги составляют значительную часть срабатываний;
- ТО проводится по фиксированным срокам, без учета фактического состояния.

Сервис должен: заранее выявлять риски отказов, снижать число ложных выездов, оптимизировать затраты на обслуживание, повышать безопасность.

## 3. Назначение и пользователи

Ключевые задачи: прогноз отказов инженерных систем, оптимизация работы диспетчерской службы и ТО, безопасность коллекторов.

Применение: мониторинг общего состояния, контроль датчиков инженерных систем и систем безопасности, планирование профилактики, аналитика при управлении инцидентами.

Пользователи:
- диспетчеры ОДС и эксплуатационных подразделений (основные);
- технический персонал;
- руководители эксплуатационных подразделений.

## 4. Постановка задачи

Сервис предиктивной аналитики для прогноза инцидентов и поддержки решений по ремонтам. Должен решать:
1. прогноз отказов датчиков и инженерных систем до их возникновения;
2. раннее выявление рисков пожаров и подтоплений;
3. аналитическая поддержка верификации несанкционированного доступа;
4. рекомендации по ТО на основе состояния оборудования.

## 5. Границы решения

| Должен | Не должен |
|---|---|
| анализировать исторические и текущие данные мониторинга | замещать диспетчеров |
| обрабатывать журналы диспетчерской службы | принимать окончательные решения об инцидентах |
| работать с реестрами оборудования | управлять оборудованием напрямую |
| давать прогноз с **вероятностью и горизонтом** | проводить ремонтные работы |
| строить модели на исторических данных | |
| интегрироваться с системами мониторинга | |

Обязан обеспечить: точность не ниже установленной, своевременное оповещение, удобный интерфейс диспетчера, надежную интеграцию, защиту данных.

## 6. Общие требования

**Прогнозирование:** анализ данных датчиков; вероятность инцидента с горизонтом **≥ 24 ч**; локация оборудования под риском; классификация типа инцидента.

**Сценарный анализ:** сценарии пожар / проникновение / подтопление по историческим данным; превентивные уведомления; рекомендации по ТО и ремонту.

**Данные:** сбор из СМВУ, журналы диспетчерской службы, реестры оборудования, статусы заявок из системы учета работ. Пример схемы СМВУ в Приложении 1.

## 7. Обработка данных

Входные данные:
- исторические: импорт CSV/XLSX;
- потоковые из СМВУ: API или очереди сообщений;
- журналы ОДС: через API;
- реестр оборудования в цифровом виде.

Данные обезличиваются на стороне источника.

Форматы: файлы CSV, XLSX; API на JSON, XML; СУБД PostgreSQL (или используемая заказчиком); геоданные GeoJSON, WKT.

## 8. Дополнительные требования (по согласованию, опционально)

- статистика по типам инцидентов, исторические отчеты по ремонтам, учет сезонности;
- модуль дообучения моделей на новых данных;
- рекомендации по профилактическому обслуживанию;
- черновики заявок на ремонт по рекомендациям;
- отчеты для руководства в PDF, XLSX.

## 9. Производительность и качество

- inference для одного объекта **≤ 5 мин**;
- потоковые данные с задержкой **≤ 5 мин**;
- работа всех пользователей одновременно без деградации;
- целевые **Precision и Recall определяет команда** на этапе проектирования, исходя из качества данных;
- горизонт прогноза **≥ 24 ч**.

## 10. Интерфейс и интеграция

UI:
- **дашборд**: веб-интерфейс диспетчера с уровнями риска;
- **интерактивная карта** объектов с проблемными зонами;
- **журнал прогнозов**: история прогнозов и результатов их отработки;
- **уведомления** о критических инцидентах в реальном времени.

Интеграция: REST API для внешних систем; чтение состояния оборудования из систем мониторинга; автоматическая синхронизация реестра оборудования.

## 11. Нефункциональные требования

| Область | Требование |
|---|---|
| Производительность | inference ≤ 300 с на объект; поток ≤ 300 с задержки; ≥ 20 пользователей одновременно |
| Надежность | доступность по регламенту заказчика; автоматические бэкапы; восстановление ≤ 4 ч |
| Безопасность | TLS 1.2+; LDAP/AD; RBAC; журнал всех действий пользователей |
| Инфраструктура | сервер на Linux; Chrome и Яндекс.Браузер; PostgreSQL 12+ |

## 12. Пользовательские сценарии

**Пожар.** Участники: диспетчер, аналитик. Условия: накоплена история инцидентов, есть интеграция с датчиками и реестром плановых работ.
1. Система сопоставляет текущие показания (температура, задымление) с плановыми работами и историческими паттернами.
2. При аномалии считает вероятность и формирует предупреждение.
3. Диспетчер получает уведомление на дашборде: вероятность, горизонт, локация.
4. Диспетчер проверяет ситуацию, при необходимости по внешним источникам (камеры).
5. Диспетчер фиксирует решение («выезд бригады», «ложное срабатывание») с причиной из справочника.
6. Решение сохраняется в журнал для анализа и **дообучения модели**.

**Подтопление.** То же, но на шаге 1 сравниваются частота включения насосных станций, прогноз метеослужб и исторические паттерны подтоплений. Решения: «бригада на проверку», «мониторинг ситуации».

## 13. Источники данных

Внутренние:
- **СМВУ**: контактные, объемные, температурные, дымовые, газовые датчики, near real-time;
- **журналы ОДС**: срабатывания, история инцидентов, глубина ≥ 12 лет;
- **реестр оборудования**: конструкции (люки, вентшахты, камеры), электрооборудование (насосы, вентиляторы), датчики.

Внешние: метеоданные через открытые API; регламент РТЭК.

Интеграция с системами заказчика только **read-only**. Хранение: оперативный контур, архив, аналитические витрины.

Что из этого реально выдано организаторами: [data.md](data.md).

## 14. Требования к решению

- все методы доступны и подробно описаны, приложен перечень библиотек и компонентов;
- решение является отдельным сервисом, может стать самостоятельной ИС или компонентом;
- сложная логика сопровождается комментариями;
- **сопроводительная документация**: методы обработки данных, условия и ограничения, инструкция по сборке и установке, функциональная и компонентная архитектура;
- открытый исходный код без обфускации;
- соответствие 149-ФЗ «Об информации…» и 152-ФЗ «О персональных данных».

## Приложение 1. Пример схемы данных СМВУ

Журнал значений каналов:

| ИД записи журнала | ИД канала данных | ИД типа канала | Текущее значение | Дата записи |
|---|---|---|---|---|
| 3 008 235 019 | 56 682 | 12 | 25,00 | 19.10.2026 12:15 |
| 3 008 235 020 | 183 582 | 12 | 25,40 | 19.10.2026 12:16 |

Реестр каналов: ИД канала → тег в дереве объектов (`56682 → МК-1.1.1.1.1.1`).

Типы каналов:

| ИД | Название | Диспетчерское название |
|---|---|---|
| 2 | contact-unlock-norm | Контакт (не замкнут – норма) |
| 3 | switch | Переключатель |
| 4 | smoke | Дым |
| 5 | movement | Движение |
| 6 | gas | Газ |
| 7 | pump | Насос |
| 8 | fan | Вентилятор |
| 9 | phase | Фаза |
| 12 | temperature | Температура |

Дерево объектов: ИД записи, ИД системы, диспетчерское название, название (`56, 168943, «Административное здание К1, пожарная система», adm-001-PS`).

Реальные выгруженные данные устроены иначе, см. [data.md](data.md).

## Приложение 2. Пример формы журнала событий

Таблица «Список событий» с фильтром по периоду и автообновлением. Колонки: время регистрации, объект, тип датчика (иконка + название: ОД, КД ОТС ДВЕРЬ, Устройство речевое), событие датчика («Норма», «Обнаружено движение»), тип события («Норма», «Предупреждение»). Строки-предупреждения отмечены красным значком.
